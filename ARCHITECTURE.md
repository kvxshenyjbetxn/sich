# Sich: архітектура (v0, базова програма)

Sich — легкий менеджер терміналів і AI-агентів на Rust + GPUI. Ключовий принцип (див. `phone-sync-plan.md`, розділ 2):
**headless-демон володіє терміналами, а UI — лише клієнт.** Закрив вікно — термінали живуть далі. Відкрив знову — бачиш той самий стан. Пізніше телефон підключиться як ще один клієнт.

## Структура workspace

```
sich/
  Cargo.toml                 workspace, edition 2024, resolver 3
  crates/
    proto/   (sich-proto)    типи повідомлень + кодек кадрів, спільні для всіх клієнтів
    daemon/  (sich-daemon)   lib: PTY-менеджер, ring buffer, IPC-сервер
    term/    (sich-term)     клієнтська модель терміналу: alacritty_terminal + keys/mouse (з ssh.client)
    hooks/   (sich-hooks)    `sich hook <agent>` (хук-CLI) + інсталятор хуків у settings.json Claude
    git/     (sich-git)      Git CLI, статус, історія, diff, операції та спостереження за worktree
    orch/    (sich-orch)     оркестрація: SQLite-пошта координатор↔воркери + чиста логіка (див. «Оркестрація»)
    app/     (sich-app)      bin `sich`: GPUI UI + підкоманди `sich daemon`, `sich hook`, `sich orch`
```

Один бінарник `sich`:
- `sich` — запускає UI. Якщо демон не відповідає, спершу стартує `sich daemon` окремим від'єднаним процесом (без консольного вікна) і чекає, поки підключиться.
- `sich daemon` — запускає демон у поточному процесі.
- `sich daemon start` — підключається до наявного демона або запускає від’єднану копію, як і GUI.
- `sich daemon stop` — надсилає демону `Shutdown`.
- `sich hook <agent>` — хук для агента (див. «Статус агентів»); диспетчеризується в `main` до будь-якої іншої ініціалізації.

## Залежності (зафіксовані версії)
- UI: `gpui-kit = "=0.10.0"` (тягне gpui-component 0.10.0 і gpui-pre 0.3.12), так само як у `E:\dev\program\ssh.client`
- `alacritty_terminal = "=0.26.0"`
- `tokio` (rt-multi-thread, sync, macros, time, io-util), `tokio-util` (codec), `futures`
- `interprocess` (feature `tokio`): local socket — named pipe на Windows, UDS на Unix
- `portable-pty`: PTY (ConPTY на Windows)
- `serde` + `postcard`: серіалізація
- `async-channel`: пробудження UI
- `notify` 8.x: нативні сповіщення про зміни у Git worktree
- `tracing` + `tracing-subscriber` + `tracing-appender`: логи
- `dirs`: шляхи
- `anyhow` / `thiserror`

## IPC
- Ім'я сокета: `sich-daemon` (namespaced: `\\.\pipe\sich-daemon` на Windows). Для тестів ім'я можна перевизначити змінною `SICH_SOCKET`.
- Кадри: `LengthDelimitedCodec` (u32 BE довжина, максимум 16 MiB), тіло — `postcard`.
- **Правило рукостискання (назавжди):** `ClientMsg::Hello` і `ServerMsg::Welcome` лишаються ПЕРШИМИ варіантами своїх enum-ів із незмінними полями, а `ClientMsg::Shutdown` приймається до `Hello` у кожній версії. При невідповідності версії демон спершу шле `Welcome { proto_version, daemon_pid }`, потім `Error` і закриває з'єднання; клієнт за цим показує «несумісний демон» і пропонує його перезапустити (старий демон v1 шле лише `Error` — це теж трактується як несумісність). Поточна `PROTO_VERSION = 7`.
- Після `Welcome` UI запитує `GetDaemonInfo`. Відповідь `DaemonInfo { build_id, proto_version, started_unix_ms }` повідомляє збірку, версію протоколу та час старту демона. За однакового протоколу інша збірка лише додає пропозицію перезапуску в статус-рядку. Несумісний протокол відкриває модальне вікно з діями «Перезапустити демон» та «Вийти». «Вийти» у цьому вікні завершує тільки UI.

### Повідомлення (`sich-proto`)
```rust
type TermId = u64;

enum ClientMsg {
    Hello { proto_version: u32, client_name: String },
    ListTerminals,
    CreateTerminal { cwd: Option<PathBuf>, shell: Option<String>, cols: u16, rows: u16 },
    Subscribe { id: TermId, resume_from_seq: Option<u64> },
    Unsubscribe { id: TermId },
    Input { id: TermId, bytes: Vec<u8> },
    Resize { id: TermId, cols: u16, rows: u16 },
    KillTerminal { id: TermId },
    Shutdown,
}

enum ServerMsg {
    Welcome { proto_version: u32, daemon_pid: u32 },
    Terminals(Vec<TerminalInfo>),          // відповідь на ListTerminals
    TerminalCreated(TerminalInfo),          // розсилається ВСІМ клієнтам
    TerminalExited { id: TermId, code: Option<i32> }, // всім клієнтам
    TerminalRemoved { id: TermId },         // всім клієнтам (після Kill або вже вийшов і прибраний)
    Output { id: TermId, seq: u64, bytes: Vec<u8> },  // seq = байтовий офсет першого байта chunk-а
    Error { message: String },
}

struct TerminalInfo { id: TermId, title: String, cwd: PathBuf, cols: u16, rows: u16, exited: Option<Option<i32>>, created_unix_ms: u64 }
```

## Демон
- tokio runtime. Кожне з'єднання — окрема задача (читання кадрів) + bounded mpsc (1024) на запис.
- **Якщо черга клієнта переповнена, з'єднання закривається.** PTY ніколи не блокується через клієнта. Клієнт перепідключиться й дотягне вивід через `resume_from_seq`.
- Термінал:
  - `portable-pty`;
  - блокуюче читання з PTY в окремому `std::thread` (буфер 64 KiB) → обробка під mutex терміналу;
  - ring buffer до 4 MiB сирих байтів з `start_seq` / `end_seq`;
  - список підписників (`conn_id` → sender).
- `Subscribe` під mutex терміналу атомарно віддає вміст буфера від `max(resume_from_seq, start_seq)` (або від `start_seq`, якщо `None`) кадрами `Output` по ≤64 KiB і реєструє підписника. Так не буває ні дір, ні дублів.
- Shell за замовчуванням:
  - Windows: `pwsh.exe`, якщо є в PATH, інакше `powershell.exe`;
  - Unix: `$SHELL`, інакше `/bin/sh`;
  - cwd за замовчуванням — домашня тека;
  - середовище: `TERM=xterm-256color`, `COLORTERM=truecolor`.
- Коли процес завершився, термінал лишається в списку з `exited`, щоб було видно вивід, доки користувач його не закриє (`KillTerminal` = вбити, якщо ще живий, і прибрати).
- Демон живе, поки не отримає `Shutdown`. Закриття UI демон не зупиняє.
- UI та `sich daemon start` копіюють поточний бінарник у `<local data>/sich/daemon-host/<build_id>/sich.exe` (`sich` на Unix). Копія публікується атомарно з тимчасового файла в тій же теці, побайтово ідентична копія перевикористовується. Якщо підготувати копію не вдалося, запуск іде з початкового шляху й пише попередження. При старті демон прибирає старі теки збірок, пропускаючи копії, що виконуються. GUI теж працює з такої копії (launcher): запуск без підкоманд (або `--takeover`), якщо процес не з host-копії, копіює себе туди, запускає копію з тими ж аргументами, cwd і env плюс `SICH_LAUNCHER_EXE=<шлях до оригінального exe>` і одразу виходить (до GPUI та single-instance; takeover робить уже копія). Тому `cargo build` працює, поки Sich відкритий; щоб оновитися, запустіть новий exe: він перебирає керування від старого GUI. Підкоманди (`daemon`, `hook`, ...) виконуються на місці. `SICH_NO_RELOCATE=1` вимикає relocation GUI; збій копіювання/запуску лише дає попередження й запуск на місці. Усе, що потребує шляху до exe для користувача (команди хуків Claude/Codex, «Restart Sich» у треї), бере `daemon_host::launcher_exe()` (`SICH_LAUNCHER_EXE`, інакше `current_exe()`); маркер не передається в `--takeover`-реплейсмент і демон. Демон стартує з host-копії від `current_exe()`: GUI і є тією копією (ідентичні байти перевикористовуються), а при запуску на місці копіюється поточний exe.
- `build_id` задається під час компіляції в `crates/app/build.rs`. Формат — версія пакета, короткий Git-хеш (або `unknown`) і час збірки в секундах UTC.
- `daemon_build_id` — окремий компіляційний ідентифікатор: 16-символьний hex FNV-1a за вмістом `crates/daemon/src`, `crates/proto/src`, їхніх `Cargo.toml` (без `Cargo.lock`: він змінюється від будь-якої нової залежності в workspace; шляхи відсортовано, CRLF нормалізується в LF; логіка в `crates/app/build_hash.rs`, спільна з `build.rs`). Демон повідомляє саме його в `DaemonInfo.build_id`, а UI порівнює з власним `daemon_build_id`, тож пропозиція перезапуску з’являється лише коли змінився код, що впливає на демон. Повний `build_id` (з часом збірки) далі визначає каталог `daemon-host/<build_id>/`.
- Логи — `<local data>/sich/logs/daemon.log`. Базова тека береться з `SICH_DATA_DIR` або `dirs::data_local_dir()` (`%LOCALAPPDATA%` на Windows).

## Клієнт `sich-term`
- Портування `ssh.client/crates/term` без SSH:
  - `TermSession` тримає `Term<Listener>` + `vte::ansi::Processor`;
  - метод `feed(seq, &bytes)` відкидає вже бачені байти за `seq`, щоб після реконекту не було дублів;
  - `last_seq()`;
  - вихідні байти (ввід, відповіді `PtyWrite`) йдуть у замикання `Fn(Vec<u8>)`, яке шле `ClientMsg::Input`.
- `keys.rs`, `mouse.rs` — без змін за змістом.

## UI `sich-app`
- Bootstrap як у `ssh.client/crates/desktop/src/main.rs`:
  - tokio runtime (2 worker-и);
  - `gpui_kit::application().with_assets(...)`, `gpui_kit::init`, тема Dark;
  - вікно 1200×760, заголовок "Sich".
- `DaemonClient` (на tokio):
  - одне з'єднання;
  - розводить `ServerMsg` по сесіях;
  - автоматичний реконект: 250 мс → 2 с backoff, без ліміту спроб;
  - після реконекту `ListTerminals` + `Subscribe` з `last_seq` кожної сесії.
  - UI будиться через `async_channel::bounded(1)`, як у ssh.client.
- Макет:
  - **Ліва панель (240 px):** список терміналів (назва з OSC title, інакше shell + cwd; позначка «exited»), кнопка `+ New terminal`, на кожному рядку кнопка закриття (`KillTerminal`).
  - **Центральна частина:** вкладки терміналів, порівнянь Git та активності субагентів. Кожна видима панель термінала має свій `TerminalView`: `prepaint` обчислює її розмір і надсилає `ClientMsg::Resize`.
  - **Перетягування з файлового менеджера:** папки, скинуті на ліву панель, додаються до списку проєктів без відкриття діалогу; звичайні файли панель ігнорує. Файли, зображення й папки, скинуті на термінал, вставляються шляхами в панель під курсором, без натискання Enter. Окреме зображення в Claude Code або Codex передається тим самим способом, що й шлях зображення з буфера обміну.
  - **Спліти терміналів:** перетягни вкладку на підсвічений край відкритої панелі, щоб розділити її ліворуч, праворуч, зверху або знизу. Між вкладеними панелями видно лінію в 1 px із зоною перетягування 6 px. У кожної панелі є компактна смужка з назвою, позначкою фокуса й кнопкою закриття термінала. Перетягни смужку у верхній рядок вкладок, щоб прибрати панель, не закриваючи термінал, або на край іншої панелі, щоб перемістити її.
  - **Меню термінала:** правий клік по вкладці або смужці дає дії «Розділити праворуч», «Розділити вниз», «Від’єднати панель» (у спліті) та «Закрити термінал». Поділ із меню відкриває новий шел у тому ж воркспейсі й теці термінала, якщо вона доступна. Запит використовує наявний `RestoreTerminal` без відтворення історії; панель додається лише для відповіді на цей запит і лише якщо цільова панель ще в розкладці. Правий клік усередині термінала, як і раніше, копіює, вставляє або передає подію TUI.
  - **Фокус панелей:** клік по видимій панелі або її вкладці дає їй фокус; вкладка прихованого термінала замінює лише активну панель. Git-порівняння та журнали субагентів тимчасово накривають розкладку, не змінюючи її.
  - **Права панель (340 px):** вкладка Git вибраного робочого дерева. Ширина змінюється перетягуванням лівої межі, подвійний клік повертає 340 px. Звичайні межі — 260–700 px, у вузькому вікні панель поступається місцем терміналу. Висоту історії комітів унизу змінюють перетягуванням її верхньої межі; подвійний клік повертає адаптивні 40%, а явна висота зберігається в сесії.
  - Внизу статус-рядок: «connected to daemon (pid N)» / «reconnecting…».
  - **Ліміти:** плашка Codex і Claude Code показує `5г` та `7д`, використані відсотки й відлік до скидання у квадратних дужках, наприклад `[через 1г 20хв]`. Клік відкриває над плашкою смуги використання й точний місцевий час скидання (для `7д` також день тижня й дату).
  - **Сповіщення:** вбудовані сповіщення Sich з’являються внизу праворуч. Новий реліз показує сповіщення з дією «Оновити», що відкриває опис релізу; повторна перевірка тієї самої версії не повертає закрите сповіщення. Ручна перевірка доступна в налаштуваннях.
- Гарячі клавіші: `Ctrl+Shift+T` — новий термінал, `Ctrl+Tab` / `Ctrl+Shift+Tab` — перемикання між терміналами.

## Швидкі команди

- Список `QuickCommand { name, command }` зберігається в `settings.json`; кнопка «▷ Команда» праворуч від директорії над терміналами відкриває меню запуску й діалог керування. Назва необов’язкова; якщо є, її показано над командою. Прев’ю команди займає один рядок і за потреби обрізається з багатокрапкою; запускається повна команда. Під час збереження крайні пробіли обрізаються, порожню команду зберегти не можна.
- Кожна швидка команда відкриває окрему тимчасову вкладку у воркспейсі й збереженій теці активного термінала. Запуск через `RestoreTerminal` зі своїм ідентифікатором запиту не надсилає ввід у вихідний термінал і не змінює його розкладку. Після першого виводу або таймера команда й `exit` відправляються в новий шел окремими натисканнями Enter (CR); це стартове введення не скасовується раннім ручним вводом.
- Завершення тимчасового шела вмикає відлік 2 хв, після якого UI видаляє лише цей термінал. Плашка використовує спільні `AutoClose` і `lifetime_banner`: «Залишити відкритим» зберігає панель із виводом завершеного процесу, а повторний дозвіл автозакриття починає нові 2 хв. Налаштування `orch_auto_close_workers` діє також на ці термінали. Стан тимчасового термінала живе в UI й не відновлюється після takeover.

## Git у правій панелі

- `sich-git` не залежить від GPUI. Блокувальний `git -C` повертає сирий stdout і помилки stderr. Читання вимикає необов’язкові блокування Git. Якщо читання впало через `index.lock`, крейт чекає на його зняття кроками по 50 мс, до 1 с, і повторює команду один раз. На Windows кожна команда Git запускається з `CREATE_NO_WINDOW`.
- Статус читається з `porcelain=v2 -z` і доповнюється лічильниками `--numstat -z` та підрахунком рядків у малих текстових файлах поза індексом. Статус обмежений 2000 записами, diff — 5000 рядками та 1 МіБ. Історія завантажується по 50 комітів, а список файлів коміту — при розгортанні. Для merge-комітів порівняння йде з першим батьком.
- `git_panel.rs` запускає Git на фоновому виконавці GPUI та приймає результати для поточного покоління вибору. Вкладка показує гілку, staged/unstaged зміни й конфлікти, історію та відкриває порівняння в центральній вкладці. Доступні stage/unstage, відкидання з підтвердженням, commit, fetch, pull з `--ff-only` і push. Чернетки комітів зберігаються для кожного worktree до виходу з програми. Панель відкривається типово та перемикається кнопкою в рядку вкладок або `Ctrl+Shift+G`.
- `notify` рекурсивно спостерігає за вибраним worktree, поки панель відкрита. Для linked worktree також спостерігає за Git-теками та їхніми refs. Фільтр відкидає тимчасові блокування, об’єкти Git, більшість reflog і типові каталоги збірки. Зміни HEAD/refs/packed-refs/logs/HEAD також оновлюють історію. Зміна вибору або закриття панелі знімає спостереження з попереднього worktree.
- Планувальник запускає одне оновлення за раз, через 80 мс після останньої події, або через 300 мс від першої при безперервному потоці. Між стартами є щонайменше 150 мс. Події під час читання об’єднуються в одне наступне оновлення. Раз на 10 с є контрольне читання. Відкриття панелі, зміна вибору, повернення фокусу та завершення операції запитують негайне оновлення.

## Вкладки порівняння

- Клік по файлу Git відкриває або активує вкладку за парою шлях/джерело в поточному worktree. Вкладки порівнянь живуть тільки в UI. Збереження сесії та IPC продовжують працювати з терміналами.
- `sich-git::compare` читає сирі blob-и та файл з диска. Робочі файли порівнюються з індексом, staged — з HEAD, файли коміту — з першим батьком, конфлікти — `stage 2` з `stage 3`. Нова або видалена сторона порожня. Кожна сторона обмежена 2 МіБ, двійкові файли визначаються за NUL у перших 8 КіБ. Перед порівнянням CRLF завжди приводиться до LF. Вкладка показує зміну стилю закінчень рядків і повідомляє, коли решта вмісту однакова.
- `similar` вирівнює рядки алгоритмом Patience. Видалення і додавання одного блоку утворюють пари з підсвічуванням відмінних фрагментів. Блоки незмінних рядків довші за шість згортаються з контекстом до трьох рядків біля змін. Обидва режими використовують той самий набір блоків. Без переносу рядки відображає `uniform_list`, з переносом — віртуалізований `ListState` зі змінною висотою вирівняних рядків.
- `diff_mode` у `settings.json` задає режим для нових вкладок, типово показ поруч. `diff_wrap_lines` зберігає налаштування переносу, типово вимкнене. Без переносу номери рядків нерухомі, а колонки мають спільний горизонтальний зсув, керований колесом, трекпадом або смугами прокрутки. `F7` та `Shift+F7` переміщуються між блоками змін. Оновлення статусу Git повторно читає відкриті робочі порівняння у фоні й зберігає позицію прокрутки. Порівняння комітів читаються тільки при відкритті.

## Статус агентів
Стан AI-агентів у терміналах (Claude Code; Gemini — лише за заголовком) живе в **демоні**, щоб його бачили всі клієнти (і майбутній телефон). Типи: `AgentKind`, `AgentState`, `AgentStatus` у `sich-proto`; `TerminalInfo.agent` і `ServerMsg::AgentStatusChanged` / `TerminalTitle` розсилаються всім клієнтам.

- **Стани:** `Working` (працює), `Waiting` (чекає користувача: дозвіл, питання, idle-prompt), `Done` (завершив хід), `Failed` (помилка), `Idle` (завершив і це вже побачено, або свіжа сесія). Немає агента = `None`.
- **`unread`:** `Stop`/`StopFailure` ставлять `unread = true`. `ClientMsg::MarkSeen { id }` (користувач подивився на термінал) скидає `unread`; `Done` стає `Idle`, `Failed` лишається `Failed`, але прочитаним.
- **Хуки (основне джерело).** Кожен термінал отримує `SICH_TERM_ID` і `SICH_SOCKET`. Claude Code викликає `"<sich.exe>" hook claude` на подіях з `settings.json`; хук читає stdin (≤ 1 МіБ), підключається до демона (500 мс), шле `Hello` + `AgentHook { term_id, agent, payload }` і завжди виходить з кодом 0, нічого не друкуючи в stdout (бюджет 2 с, watchdog). Поза Sich (`SICH_TERM_ID` немає) хук одразу виходить.
- **Відображення подій Claude** (чиста функція `agent::apply`): `UserPromptSubmit`, `PreToolUse`, `PostToolUse`, `PostToolUseFailure`, `SubagentStart` → Working; `PermissionRequest`, `Notification`, `Elicitation`, `PreToolUse` з `AskUserQuestion` → Waiting; `Stop` → Done (unread); `StopFailure` → Failed (unread); `SessionStart` → Idle; `SessionEnd` → None. `PostToolUse` протягом 1 с після `Stop` ігнорується.
- **Fallback за заголовком** — лише поки термінал не отримав жодного хука в поточній сесії агента. Демон сканує вивід PTY (`osc.rs`, інкрементально, через межі чанків): OSC 0/2 (заголовок, ≤ 256 символів) і BEL. Claude: брайлівський спінер U+2800–28FF або ◐◓◑◒ → Working, ✳ → Idle (або Done + unread, якщо було Working). Gemini: ✦ / ⏲ → Working, ◇ → Idle/Done, ✋ → Waiting. Прості заголовки після Idle/Done означають вихід агента.
- **Багатий рядок (протокол v5).** `AgentStatus` має ще `model`, `title`, `prompt`, `message` (поряд із `detail`). Джерела — документовані поля вводу хуків (для Claude transcript не потрібен): `SessionStart.model` / `session_title`; `PostModelSwitch.to_model` (Claude Code >= 2.1.251, подія ставиться інсталятором лише для такої версії); `UserPromptSubmit.prompt` (блоки `<pasted_content>…</pasted_content>` замінюються на «[…]»); `PreToolUse`/`PermissionRequest`/`PostToolUse` → `detail` = `Bash: <команда>` або `Edit|Write|Read: <ім'я файлу>` (інакше назва інструмента, ≤ 120 символів); `Notification.message`; `Stop`/`SubagentStop`/`StopFailure.last_assistant_message` → `message`. Текст нормалізується (`agent::normalize_text`: пробіли/переноси → один пробіл, trim, ≤ 400 символів з «…»). Липкість у `apply`: `model` і `title` лишаються до скидання статусу (`SessionEnd`/вихід процесу); `prompt` ставиться на `UserPromptSubmit` і лишається; `message` скидається на `UserPromptSubmit`, ставиться на `Stop`/`SubagentStop`/`StopFailure`. `PostModelSwitch` і `SubagentStop` не змінюють стан (лише `model` / `message`; без статусу — ігноруються).
- **Субагенти Claude (протокол v6).** `AgentStatus.subagents: Vec<SubagentStatus>` (`id`, `agent_type`, `description`, `state` Working|Waiting, `detail`, `since_unix_ms`), максимум 16 на термінал. Атрибуція — за `agent_id` у вводі хуків: події `PreToolUse`/`PostToolUse`/`PostToolUseFailure`/`PermissionRequest`/`Notification`/`Elicitation` з `agent_id` оновлюють лише запис цього субагента (Working з міткою інструмента або Waiting) і НЕ змінюють основний статус; без `agent_id` — подія основного агента. `SubagentStart` додає запис; опис береться з черги `pending_spawns` (стан `AgentTracker`, не протокол): основний `PreToolUse` інструмента `Agent`/`Task` кладе туди `{subagent_type, description}`, старт бере перший збіг за типом (без регістру), `PostToolUse` основного `Agent` видаляє незабраний запис, `Stop`/`SessionStart`/`SessionEnd`/вихід очищають чергу (ліміт 16). `SubagentStop`/`StopFailure` з `agent_id` прибирають запис. Події `agent_id` з префіксом `hook-agent-` ігноруються. Якщо `Stop`/`SubagentStop` несе `background_tasks` (масив) — реєстр звіряється: записи, яких немає серед «запущених» (типи `local_agent`/`local_subagent`/`subagent`, термінальні статуси — не запущені), видаляються, нові запущені додаються; без поля реєстр лишається як є. `SessionStart`/`SessionEnd`/вихід очищають реєстр; `UserPromptSubmit` — ні (фонові субагенти можуть працювати). Плейсхолдери «unknown/untitled/task/subagent» вважаються відсутніми підписами. UI: `badge_for` бере найвищий пріоритет серед основного бейджа й бейджів субагентів (Waiting субагента піднімає рядок/вкладку/воркспейс і дає `should_flash`); у сайдбарі під рядком агента — до 4 дочірніх рядків (24 px: бейдж, підпис, деталь, час; клік активує термінал) і рядок «ще N субагентів». Субагенти Codex описані нижче, в розділі «Codex hooks».
- **Рядок у сайдбарі.** Домівка показує список із першого термінала, а worktree — якщо терміналів ≥ 2 або в будь-якого є агент (`sub_list_ids`). Шеврон Домівки згортає термінали та вкладених субагентів без перемикання воркспейсу або закриття терміналів; у згорнутому стані заголовок показує зведений статус агентів. Термінал з агентом — дворядковий (44 px): бейдж, гліф агента (✳ Claude `#D97757`, ✦ Gemini `#4796E3`, інакше «•»), заголовок (`title`, інакше назва вкладки), модель (`shorten_model`: без `claude-`), відносний час (`i18n::relative_time`: щойно/5хв/2год/3д) і приглушене прев'ю (`agent_preview`: Waiting/Working → `detail`, інакше `prompt`; Done/Idle → `message`, інакше `prompt`; Failed → `message`, інакше `detail`). `AppView` перемальовує UI кожні 30 с, поки є агенти, щоб оновлювався час.
- **Заголовок терміналу** тепер живий OSC-заголовок із демона (`TerminalInfo.title`, `TerminalTitle`), без нього — назва шела.
- Завершення процесу або видалення терміналу скидає статус у `None`.
- **Інсталятор** (`sich-hooks::claude_install`): додає наші записи (`{"type":"command","command":"\"<exe>\" hook claude","timeout":5}`) у `~/.claude/settings.json` (або `CLAUDE_CONFIG_DIR`). Лише події, відомі встановленій версії Claude (`claude --version`; невідома версія → стабільний набір). Користувацькі хуки та порядок ключів зберігаються, перед першою зміною створюється `settings.json.sich-backup`, запис атомарний, некоректний JSON не чіпається. Наші записи впізнаються за командою `…/sich[.exe] hook claude`, тож перевстановлення замінює старий шлях.

### Codex hooks

Статус OpenAI Codex CLI відстежується офіційними хуками `hooks.json` (docs: learn.chatgpt.com/docs/hooks); `crates/hooks/src/codex_install.rs`, UI-стан у `crates/app/src/codex_hooks.rs`, перемикач у налаштуваннях (`codex_hooks`, за замовчуванням true; `SICH_NO_HOOK_INSTALL` вимикає автоінсталяцію).

- Розташування: `$CODEX_HOME/hooks.json`, за замовчуванням `~/.codex/hooks.json`. Команда: `<sich.exe> hook codex` (шлях з `/`, у лапках лише якщо є пробіли). Наші записи впізнаються за формою команди; чужі хуки й порядок ключів не чіпаємо; бекап `hooks.json.sich-backup` перед першою зміною; зіпсований файл не змінюємо.
- Події: SessionStart, UserPromptSubmit, PreToolUse, PermissionRequest, PostToolUse, Stop (таймаут 5 с), SubagentStart і SubagentStop (5 с, з 0.133), Interrupt і SessionEnd (3 с). Версія з `codex --version`: нижче 0.129 або невідома → нічого не ставимо; Interrupt і SessionEnd лише з 0.150 (мінімальну версію SessionEnd з документації підтвердити не вдалося, тому гейт як у Interrupt).
- Довіра: увімкнений `codex_hooks` дозволяє Sich автоматично схвалювати свої хуки під час встановлення, зокрема при старті UI. Фоновий клієнт `codex app-server` з обмеженим часом звіряє команду, файл і позицію через `hooks/list` та оновлює лише `trusted_hash` потрібних записів через `config/batchWrite`. Ключ довіри містить шлях, подію та індекси групи й хука, тому нова група додається в кінець, а наявний запис замінюється на місці. Перед першим записом створюється `config.toml.sich-backup`. Вимкнення прибирає наші хуки та схвалені Sich хеші, що досі збігаються з `codex-hook-trust.json` у конфігурації Sich. Помилка схвалення залишає хуки встановленими та показує підказку про `/hooks`.
- Демон: `agent::parse_codex_payload` + `apply_codex` (SessionStart→Idle, UserPromptSubmit→Working, Pre/PostToolUse→Working з міткою інструмента, PermissionRequest→Waiting, Stop→Done+unread, Interrupt→Idle без unread, SessionEnd→очищення; `model` оновлюється на кожній події).
- **Субагенти Codex** (той самий `AgentStatus.subagents`, UI не залежить від виду агента). Події `SubagentStart`/`SubagentStop` ставимо з Codex 0.133. Будь-яка подія, яку породив субагент, має верхньорівневий `agent_id` (без нього — головний агент); child-хуки йдуть у те саме середовище терміналу. Правила `apply_codex`: з `agent_id` події SubagentStart/Pre/PostToolUse/PermissionRequest оновлюють запис субагента (Working/Waiting, `detail` — мітка інструмента або опис), SubagentStop/Stop прибирають його, усе інше (зокрема child SessionStart) ігнорується; головний статус, `model` і `message` від child-подій не змінюються, а без наявного статусу child-подія його не створює. SubagentStart/SubagentStop без `agent_id` ігноруються. Кореневі SessionStart, Stop (CLI інколи губить child-стопи, як і в Orca) та Interrupt очищають весь ростер; UserPromptSubmit ростер зберігає; SessionEnd скидає статус. Максимум `MAX_SUBAGENTS`.
- **Назва субагента Codex** (`codex_rollout.rs`). З child-хука беремо `transcript_path` (лише абсолютний, що закінчується на `.jsonl`) і читаємо ТІЛЬКИ перший рядок цього rollout-файлу (не більше 256 КіБ, лише читання, вміст не логуємо): `session_meta`, де `payload.id == agent_id`. Мітка: шлях-мітка з `thread_spawn.agent_path` (інакше `payload.agent_path`; без початкового сегмента `root`, решта через `/`), далі `thread_spawn.agent_nickname`, далі `payload.agent_nickname`; результат іде в `description` субагента. Результат читання: Found / Pending (файлу немає, він порожній або перший рядок ще неповний) / Miss (повний рядок без ідентичності або не JSON) / Unreadable. Облік у `AgentTracker.identities` (не в протоколі): Named — більше не читаємо; Missed(path) — не повторюємо для цього шляху; Pending(path, len) — повторюємо на наступній child-події лише якщо довжина файлу змінилась; Unreadable — не раніше ніж за 5 с. Записи видаляються, коли субагент залишає ростер (або ростер очищено). Рішення «чи читати» приймає `AgentTracker::identity_plan` під локом, сам невеликий синхронний читання (`codex_rollout::execute`) виконується ПОЗА локом у `Terminal::agent_hook`, потім `on_codex_hook_with` застосовує хук і результат разом. Ми, на відміну від Orca, не читаємо хвіст rollout батьківського агента (`sub_agent_activity`): стан субагента береться лише з хуків.

### omp hooks

- Sich використовує офіційне [розширення omp](https://github.com/can1357/oh-my-pi/blob/v19.0.1/docs/extensions.md), як і Orca. Перемикач «Відстежувати стан omp» (`omp_hooks`, типово увімкнений) вимагає omp 19.0.1 або новіший. Автоінсталяція враховує `SICH_NO_HOOK_INSTALL`.
- Інсталятор запитує `omp config path` і додає тільки власний файл `extensions/sich-omp-status.js` до активного для GUI профілю. Конфігурацію агента не переписує. Вимкнення видаляє лише файл із міткою Sich, за шляхом у `omp-hook.json` Sich; нові запуски omp підхоплюють зміну. Для профілю, вибраного лише аргументом `--profile`, можна явно додати цей файл через `--extension <шлях>`. `--no-extensions` вимикає автоматичне завантаження.
- Нове покоління демона передає у свій PTY `SICH_OMP_HOOK` (шлях до свого бінарника). Головний статус змінюється лише за подіями основної TUI-сесії: старт/перемикання → Idle, промпт/інструмент → Working, підтвердження інструмента, форма `ask` або перегляд плану → Waiting, завершення → Done або Failed, скасування → Idle, вихід → очистити статус. Знімки йдуть як JSON через `sich hook omp` і той самий локальний IPC. Поза Sich розширення нічого не робить і не читає транскриптів.
- **Субагенти omp.** Розширення слухає [`task:subagent:lifecycle` і `task:subagent:progress`](https://github.com/can1357/oh-my-pi/blob/v19.0.1/docs/tools/task.md#side-effects): фактичний старт додає рядок, прогрес оновлює опис і назву інструмента, завершення/помилка/скасування прибирають рядок. `ask` і запит дозволу переводять лише відповідного субагента в Waiting. Дочірні екземпляри розширення передають вкладені події в основну сесію через `BroadcastChannel`, у тому числі з потоків воркерів omp. У кожному знімку — до 16 активних субагентів у порядку старту (`AgentStatus.subagents`), без аргументів інструментів чи виводу. Перемикання сесії очищає список; дитячі оновлення не скидають позначку прочитаного ходу.
- Протокол лишається v7: клієнт із суфіксом `+omp` у `Hello.client_name` отримує `AgentKind::Omp`; решта бачать універсальний `Other`. Старі покоління не завантажують інтеграцію, їхні термінали не перезапускаються.

### Вкладки активності субагентів

- Для omp, Codex і Claude Code клік по активному субагенту відкриває або фокусує окрему вкладку поточного воркспейсу. Вона лише для перегляду: не приймає ввід термінала, не позначає батьківський хід прочитаним і не перериває роботу агента при закритті. Після зникнення рядка з сайдбару відкрита вкладка зберігає отримані записи.
- Підтверджене журналом завершення запускає відлік 2 хв. Вкладка має спільну з воркерами Sich плашку «Тимчасовий» / відлік і дії «Залишити відкритим» та «Дозволити автозакриття». Повторний дозвіл після завершення запускає нові 2 хв. Налаштування автозакриття діє і на воркерів, і на вкладки субагентів; втрата IPC-з’єднання не вважається завершенням. Автозакриття прибирає лише вкладку журналу, а не термінал батьківського агента.
- Рядок активного субагента в сайдбарі показує його модель, якщо джерело повідомляє її явно: повідомлення самого субагента в omp або атрибутовані йому хуки Codex / Claude Code. Якщо модель невідома, поле порожнє — модель батьківської сесії не підставляється.
- Другий, приглушений рядок під назвою показує останню дію субагента: мітку інструмента або те, на що він чекає. Без повідомленої дії рядок лишається однорядковим. В omp остання мітка інструмента зберігається між викликами.
- У заголовку вкладки перемикаються два вигляди тих самих записів: **Хронологія** (типово) з кольоровими позначками й окремими блоками повідомлень та **Термінал** — компактний моноширинний лог. Вибір діє для відкритої вкладки. Перемикання зберігає історію та позицію прокрутки і не відкриває нове IPC-з’єднання.
- Демон тримає в пам’яті до 48 запусків на термінал (до 128 останніх записів на запуск), від початку, а не від першого кліку. Ключ включає вид агента, ID батьківської сесії, ID субагента та час початку запуску. omp надсилає події інструментів, очікування, видимий фіналізований текст і результат запуску (`task:subagent:event` / `task:subagent:lifecycle`); Claude Code і Codex — доступні інструменти, результати, дозволи й останню відповідь з офіційних дочірніх хуків. Це журнал дій, а не повний транскрипт. Аргументи інструментів, приховані міркування та сирі тіла подій у журнал не записуються.
- `GetSubagentActivity` / `SubagentActivity` доповнюють v7 без зміни наявних форматів. Вкладка читає прирости за номером останнього запису через окреме IPC-з’єднання з демоном-власником термінала. Можливість `subagent_activity` оголошує реєстр поколінь; на попередньому поколінні вкладка показує, що журнал недоступний, і не надсилає нових IPC-запитів. Історія не пишеться на диск і не розсилається іншим клієнтам.
- Моделі в протоколі v7 передаються разом зі знімком терміналів або оновленням агента, лише коли клієнт запросив `+subagent-models` перед `+omp` у `Hello.client_name`. Реєстр поколінь оголошує `subagent_models`; старі клієнти отримують старий формат, а старі демони продовжують працювати без позначок моделей.

## Групи проєктів (протокол v4)
- `GroupId = u64`, `GroupInfo { id, name }`, `ProjectInfo.group: Option<GroupId>`. `ServerMsg::Projects { projects, groups }` (відповідь на `ListProjects` і розсилка всім клієнтам після будь-якої зміни). `ClientMsg::AddProject { path, group }`; нові команди в кінці enum-а: `CreateGroup`, `RenameGroup`, `RemoveGroup`, `SetProjectGroup`.
- Демон зберігає групи в `projects.json` (`SICH_CONFIG_DIR`): об'єкт `{ groups, projects, next_group_id }`. Старий формат (голий масив проєктів, без `group`) читається як є. Id груп зростають і не перевикористовуються в межах файлу.
- Імена: обрізаються; порожнє або дубль без урахування регістру (крім перейменування на власне ім'я) → `OpFailed`. `RemoveGroup` не видаляє проєкти, а лише розгруповує їх. Невідомий id групи в будь-якій операції → `OpFailed`, без змін. Порядок: групи за створенням, проєкти в наявному порядку.
- Бічна панель: Home, далі групи (шеврон, іконка, назва; у згорнутому стані роллап-бейдж `group_badge`), далі проєкти без групи. Проєкти всередині розгорнутої групи мають додатковий відступ. Стан згортання (`collapsed_groups`) живе на клієнті; вибір worktree розгортає його проєкт і групу. Чисті функції — `groups.rs` (`group_projects`, `group_badge`, `expand_to`).
- Щоб перемістити вже додану папку між групами або з-поза групи, перетягни її рядок на заголовок потрібної групи. Ціль підсвічується й розгортається після скидання. Як і пункт «Перемістити до групи», ця дія лише змінює групу: папка на диску лишається на місці.

## Трей, один екземпляр, сесія UI
- **Трей (Windows, `tray.rs`, крейт `tray-icon` 0.26).** Іконка з ресурсу `1 ICON` (`app.rc`), меню «Показати Sich» / «Перезапустити Sich» / «Вийти з Sich» (мова слідує за налаштуванням), підказка `tray_tooltip` («Sich — 1 waiting, 2 working»). Створюється на головному потоці GPUI після відкриття вікна; події трею/меню йдуть через `futures::mpsc::unbounded` у цикл `AppView` (`UiEvent::Show` / `Restart` / `Quit`). На не-Windows трею немає (`Tray::new` повертає помилку).
- **Закриття вікна.** `window.on_window_should_close` завжди повертає `false` і віддає рішення `AppView`: при `close_to_tray` (налаштування, типово `true`) і наявному трею вікно ховається через `ShowWindow(SW_HIDE)` (`win_show.rs`); демон і термінали живуть далі. Показ: `SW_SHOW`/`SW_RESTORE` + `SetForegroundWindow`. Без трею або при `close_to_tray = false` закриття = вихід.
- **Вихід** (пункт трею або закриття без трею): якщо є термінал з агентом у стані Working/Waiting (`needs_quit_confirm`), вікно показується і з'являється підтвердження; далі синхронно зберігається сесія, демону йде `Shutdown` (як `sich daemon stop`), `cx.quit()`.
- **Один екземпляр (`single_instance.rs`).** Local socket `<SICH_SOCKET>-ui` (`sich-daemon-ui` за замовчуванням). Новий UI надсилає рядок `hello <build_id>` й отримує `build <build_id>`. Однакова збірка надсилає `show` й завершується. Інша надсилає `takeover <build_id>` і чекає на звільнення сокета до 5 с. Старий UI синхронно зберігає сесію й завершується без `Shutdown`. Новий UI під’єднується до наявних терміналів і відновлює вибір вкладок за їхніми ID. «Перезапустити Sich» зберігає сесію й запускає той самий бінарник з `--takeover`, щоб передати UI навіть за однакового `build_id`. Збірка, яка розуміє лише `show`, отримує цей запит.
- **Сесія (`session.rs`, `<config>/sich/session.json`, `SICH_CONFIG_DIR` враховується).** Зберігаються вибір, workspaces, згортання Домівки, проєктів і груп, межі вікна й стан панелей. Для кожного живого терміналу — ID, cwd, відомий агент і, при перезапуску демона, ім’я файла скролбеку. ID терміналів прив’язані до PID демона в сесії. Поля мають `serde(default)`. Старі файли читаються, пошкоджені ігноруються з попередженням.
- **Збереження.** `AppView::touch_session` (з `on_wake`, `sync`, зміни меж вікна) будує `Session` чистою `build_session` і, якщо вона змінилась, планує запис через 500 мс (атомарно tmp + rename). Перед виходом — синхронний запис. Поки відновлення не завершене (`session_ready`), файл не перезаписується.
- **Розкладка терміналів:** `terminal_layout.rs` веде дерево панелей окремо для кожного воркспейсу. `session.json` зберігає напрям і частку кожного поділу та індекси терміналів у списку воркспейсу, а не тимчасові ключі GUI. Індекси зіставляються з живими терміналами за власником або з відповіддю на відповідний `RestoreTerminal`; гілки без терміналів згортаються. Спліти не потребують змін протоколу чи перезапуску демона.
- **Відновлення.** `window_placement` відновлює межі вікна (мінімум 640×400; позиція поза екранами → центр). При першому `Projects` UI відновлює згортання й вибір; `session.selected` має пріоритет над `settings.last_workspace`. Після першого повного списку терміналів UI під’єднує наявні за ідентичністю, не відтворює закриті на живому демоні й відтворює термінали відсутніх демонів через `RestoreTerminal`. Якщо cwd зникла, береться тека worktree або домівка; відсутні worktree пропускаються. Якщо терміналів немає й відновити нічого, відкривається один Home.

## Покоління демонів поруч (той самий PROTO_VERSION)
- Кожен демон слухає `<base>-<daemon_build_id>`, де `base` — `SICH_SOCKET` або типове ім'я. Крім того, демон пише запис `<data>/sich/daemons/<daemon_build_id>.json` (`pid`, `socket`, `daemon_build_id`, `proto_version`, `started_ms`) і видаляє його при виході; читачі прибирають записи з мертвим `pid` (реєстр під файловим локом). Логіка в `crates/daemon/src/generation.rs`.
- Після оновлення, що змінило код демона, новий GUI запускає НОВЕ покоління (спільний шлях spawn/relocation із `daemon_host`), а старе лишається з його терміналами. Демон попередньої версії слухає неіменоване `base`: GUI один раз пробує це ім'я й трактує його як legacy-покоління (не вбиває і не перезапускає).
- `DaemonPool` (`daemon_client.rs`): primary — власний `daemon_build_id` (сюди йдуть усі нові термінали, проєкти, групи, worktree); legacy — решта демонів того ж `base` і протоколу, GUI лише показує й керує їхніми існуючими терміналами. Реєстр опитується кожні 0,5 с.
- Ідентичність терміналу: `TermId` колізяться між демонами, тому GUI використовує власні монотонні ключі, що відображають `TerminalOwner { socket, id, pid, created_ms }`. Усе (робочий простір, вкладки, бічна панель, оркестрація) оперує цим ключем; команди (`Input`, `Kill`, `MarkSeen`) іду́ть до демона-власника, а `pid`/`created_ms` захищають від повторного використання id.
- Сесія: кожен збережений термінал має `socket`, `daemon_pid`, `created_ms`; при відновленні `session::reattach` підключає живі термінали за власником, перестворює лише ті, чий власник мертвий, і ніколи не поповнює демон, що вже відповів. Старі файли без цих полів читаються як legacy-ім'я.
- Оркестрація: база `orchestration.db` має додаткові таблиці `run_sockets`, `dispatch_sockets`, `socket_deliveries` (лише `CREATE IF NOT EXISTS`, старі виконувані файли відкривають БД). Рядки без сокета належать legacy-імені. Спостерігач мапить `(socket, term_id)` у ключ GUI. `sich orch …` говорить із демоном зі свого `SICH_SOCKET`; нові воркери створюються на найновішому сумісному поколінні. Хуки (`sich hook`, `sich statusline`) використовують `SICH_SOCKET` терміналу, тобто його власний демон.
- Виведення з експлуатації: legacy-з'єднання GUI відкривається з іменем клієнта `sich-app-retire-when-empty`; щойно такий демон показав порожній список, GUI шле `Shutdown`, який для цього клієнта діє лише якщо терміналів справді нема. Окремо покоління з реєстром виходить саме, якщо без терміналів уже 30 с і існує новіше сумісне покоління. Демон із терміналами не зупиняється ніколи.
- «Перезапустити демон» лишається лише при розбіжності PROTO_VERSION. Якщо є термінали старіших сумісних поколінь, жовта кнопка поруч із зеленим індикатором з’єднання пропонує в підказці перезапустити їх усі. Клік послідовно переносить лише ці термінали на поточний демон, перевикористовуючи відновлення одного термінала. Вихід із Sich (`Quit`) зберігає сесію й зупиняє всі підключені демони.
- Термінали попереднього покоління мають кнопку перед назвою у верхній вкладці та в правому кінці рядка бічної панелі, після кнопки закриття. Вона перезапускає лише цей термінал на поточному демоні без зміни протоколу: UI зчитує до 512 КіБ виводу через `Subscribe`/`Unsubscribe`, відтворює його після підтвердженого `RestoreTerminal` і заміняє термінал у розкладці сплітів. Старий PTY видаляється лише після створення заміни. Як при повному перезапуску, процеси не переносяться наживо, а підтримувані сесії агентів відновлюються за налаштуванням.

## Перезапуск демона й відновлення терміналів (протокол v7)
- Після підтвердження UI запитує `SaveScrollback` і за відповіддю `ScrollbackSaved { files }` додає імена файлів до `session.json`. Запис сесії передує `Shutdown`. Коли сокет звільняється, UI запускає демон поточної збірки й перепідключається. Для демона до v7 використовується остання збережена сесія.
- Демон зберігає останні 512 КіБ сирого кільцевого буфера кожного живого терміналу в `<config>/sich/scrollback/<term_id>-<started_ms>.bin`. `Shutdown` оновлює ці знімки перед закриттям терміналів. Тека обмежена 128 файлами та 64 МіБ. Знімки, старші за 7 днів, прибираються при старті демона та збереженні.
- `TerminalRestored` повертається тому клієнту, який запросив `RestoreTerminal`, з тим самим ID запиту. До підписки на живий вивід UI відтворює знімок лише в емуляторі, додає приглушений розділювач і видаляє файл. Відтворення не надсилає термінальні відповіді чи команди до PTY. Для агента, що був `Working`, UI додає попередження про перервану роботу.
- `AgentStatus.session_id` береться з кореневого хука Claude/Codex, зберігається між подіями й очищується на `SessionEnd`. Періодичний запис сесії зберігає ці ID й дозволяє відновлювати агентів після аварійного завершення. За налаштуванням `resume_agents_on_restore` (типово ввімкнено), після першого виводу шела або через 1,5 с UI вводить `claude --resume <id>` чи `codex resume <id>`. ID має 8–64 символи ASCII (літери, цифри або дефіси) й не починається з дефіса.

## Оркестрація (`crates/orch`, `sich orch …`)

Агент-координатор (наприклад Claude Code в терміналі Sich) запускає Claude Code, Codex або omp у нових терміналах, дає воркерам задачі й отримує питання та результати. Sich будить координатора, коли приходить пошта. Воркери запускаються офіційними CLI з власним логіном користувача; стан береться з хуків, а команди оркестрації визначають термінал за `SICH_TERM_ID` і `SICH_SOCKET`.

- **Крейт `sich-orch`** (без GPUI): `db` (SQLite, `rusqlite` bundled), `model`, `paths`, чисті модулі `preamble`, `launch`, `dialogs`, `delivery`, `escalation`, `cli_parse` та `watch` (один «тік» GUI-спостерігача над тимчасовою БД).
- **БД** `<config>/sich/orchestration.db` (`SICH_CONFIG_DIR` враховується): WAL, `busy_timeout` 5 с, таблиця `schema_version` + міграції під `BEGIN IMMEDIATE`. Таблиці `runs` (один активний run на термінал-координатор), `tasks`, `dispatches` (стани `starting|working|done|failed|lost|released`), `messages` (типи `message|question|reply|worker_done|escalation`, `payload` JSON для `worker_done` та ескалацій), `deliveries` (останній набраний вказівник на термінал). Id: `r_/t_/d_` + 8 hex. Id терміналів перевикористовуються після рестарту демона, тому run прив'язаний до часу створення терміналу (`created_unix_ms`): рядки старішого покоління ігноруються.
- **CLI** (`crates/app/src/orch_cli.rs`, той самий бінарник; `main` віддає `orch` до relocation GUI): особа визначається за `SICH_TERM_ID` (поза Sich — помилка). `start` (спека → task-файл `<config>/sich/orch/tasks/<task>.md` з преамбулою → `CreateTerminal` у тому ж cwd/worktree → `Subscribe` → чекає промпт шела: перший вивід + 800 мс тиші, макс. 10 с; на запит курсора `ESC[6n` відповідає лише якщо ніхто не відповів за 700 мс (зазвичай відповідає GUI) → набирає команду запуску → чекає до 90 с, поки `AgentStatus` стане Working/Done/Waiting). Результат: `state=working` (код 0), `state=blocked reason=…` (діалог у виводі; термінал лишається користувачу, код 1), `state=unknown` (таймаут) або `state=failed reason=terminal-exited`. `send`, `check` (споживає непрочитане), `ask`, `reply`, `done` (рівно раз; після нового повідомлення воркер знову відкривається), `list`, `release` (`KillTerminal`). Прихований тестовий хук: `SICH_ORCH_FAKE_AGENT=<програма>` замінює `claude`/`codex`, `SICH_ORCH_READY_TIMEOUT_MS` — таймаут готовності. Значення `--model`/`--effort` і шлях task-файлу (без `"`, `` ` ``, `$`, переводів рядка) перевіряються суворо до будь-яких побічних ефектів.
- **Воркер omp.** `sich-cli orch start --agent omp --model openai/gpt-5.4 --effort high --spec-file task.md` (модель і рівень міркування необов'язкові). Потрібні omp 19.0.1+, встановлене та ввімкнене відстеження omp у Sich і налаштований провайдер. `start` передає кероване розширення як `--extension`, щоб запуск не залежав від того, який профіль бачить новий shell. Окремий `--session-dir` поряд із task-файлом гарантує нову сесію навіть із `autoResume`; `--effort` стає `--thinking`, а `--auto-approve` передається лише коли дозволено налаштуванням автономних воркерів. `start` чекає саме на статус omp; звичайний `Idle` не вважається початком роботи. Початкове налаштування або відсутня модель повертають `state=blocked`, залишаючи термінал відкритим.
- **Міграція БД v4** розширює список видів воркерів на `omp`, зберігаючи поточні завдання, сокети й worktree. Для команд `orch` після міграції потрібен новий `sich-cli`; оновлення не зупиняє демони або відкриті термінали.
- **Діалоги** (`dialogs`): у виводі нового терміналу (після зняття ANSI) шукаються «hooks need review», «Review hooks», «Do you trust», «trust this folder», «Yes, I trust», «Press enter to confirm». Sich їх **ніколи не підтверджує** сам.
- **`sich-cli`** (`crates/app/src/bin/sich_cli.rs`, std only, console subsystem): `sich.exe` у release є GUI-subsystem, тож PowerShell не чекає на нього, не показує stdout і не ставить `$LASTEXITCODE`. `sich-cli orch|daemon …` запускає `sich.exe` поруч із собою (або `SICH_EXE`) з тими самими аргументами, stdin успадковує, stdout/stderr читає через pipe у двох потоках і побайтово копіює у свої, виходить з кодом дитини (1, якщо не стартував чи був убитий). Без аргументів чи з невідомою підкомандою друкує usage й виходить з кодом 2 (GUI не запускає). Усі підказки агентам/користувачу (скіл, преамбула воркера, вказівник пробудження) використовують `daemon_host::cli_exe()` = `sich-cli.exe` поруч із `launcher_exe()`, а якщо його немає — `sich.exe` (одне попередження в лог). Relocation копіює лише `sich.exe`; `sich-cli.exe` запускається з місця збірки/встановлення (короткоживучий, блокування не заважає).
- **Доставка** (`delivery`, `watch`): спостерігач GUI щоп'ятисот мс (поки БД існує) для термінала з непрочитаною поштою набирає `You have N Sich orchestration message(s). Run \`<exe> orch check\`.` як bracketed paste, через 300 мс — Enter, і записує це в `deliveries`. Умови: агент `Done`/`Idle` і незмінний ≥ 1,5 с; користувач не друкував у цьому терміналі ≥ 3 с (`orch_watch::note_user_input` з `TerminalView`); нова пошта (id більший за вказаний) — одразу, та сама непрочитана — не частіше ніж раз на 60 с. Ніколи для `Working`/`Waiting` та для терміналу без агента.
- **Ескалації** (`escalation`): диспетчеризація в `working`, агент якої завершив хід (`Done`/`Idle`/`Failed`) ≥ 5 с тому після останнього завдання/повідомлення без `worker_done` → одна ескалація `stopped without reporting`; термінал зник/завершився → `lost` + ескалація `exited`. Дублі виключені; без повного списку терміналів від демона висновки не робляться.
- **Сайдбар**: кеш `OrchSnapshot` оновлює спостерігач (у `render()` запитів до БД немає). Воркер без іншого прев'ю показує `worker · <назва задачі>`, термінал-координатор — приглушену позначку `coord` поруч із заголовком.
- **Скіл Claude Code** (`orch_skill.rs`, налаштування `orchestration_skill`, типово true, перемикач у налаштуваннях): при старті GUI пише `<claude config>/skills/sich-orchestration/SKILL.md` (абсолютний шлях exe всередині, маркер `<!-- sich:managed … -->`). Файл без маркера не перезаписується й не видаляється; вимкнення прибирає наш файл і теку. Debug-збірка і `SICH_NO_HOOK_INSTALL` автоінсталяцію пропускають.
- **Worktree воркерів**. `start --worktree <name>` створює нову гілку від поточної локальної гілки координатора через `CreateWorktree` та відкриває термінал через `RestoreTerminal` з ідентифікатором запиту. У БД зберігаються шлях, гілка, базова гілка та власник, а Git-метадані worktree містять ідентифікатор диспетчеризації. `release --remove-worktree` закриває воркера й примусово видаляє його worktree та гілку. Щопівхвилини фоновий спостерігач GUI перевіряє worktree у стані `released` або `lost`. Якщо `orch_cleanup_worktrees` увімкнено, він видаляє чистий worktree без живих терміналів після злиття гілки в записану базову гілку. Демон перевіряє власника і повторно перевіряє умови безпечного видалення.
- **Ще не зроблено**: залежності між задачами (DAG), перевідкриття воркера після виходу його терміналу, віддалені/мобільні клієнти, `--wait` для `ask`, JSON-вивід CLI.

## Зображення в терміналі (`crates/term`, `crates/app/src/term_images.rs`)
- Конвеєр (на клієнті, у `TermSession::feed` і `replay_history`):
  - `intercept.rs` — потоковий фільтр байтів PTY: усе звичайне йде в alacritty без змін і в тому ж порядку, а команди зображень виймаються окремо (працює, коли послідовність розрізана між `feed`; ліміт 8 МБ на послідовність, більша відкидається з ресинком);
  - перед командою всі попередні байти вже застосовано, тож курсор відомий; якщо відкрито блок DEC 2026, його буфер скидається (`stop_sync`);
  - `inline.rs` застосовує команду: зберігає зображення, пише клітинки в сітку, рухає курсор, формує відповіді.
- Підтримано:
  - **Kitty graphics**: `a=t/T/p/d/q`; формати `f=100` (PNG і будь-який формат `image`), `f=24/32` з `s`/`v`; `o=z`; передавання `t=d` (чанки `m=1…0`), `t=f`, `t=t` (видаляється лише файл у системній temp-теці з `tty-graphics-protocol` в імені); `c`/`r`, `x`/`y`/`w`/`h`, `C=1`, `q=1/2`, `i`/`I`/`p`; видалення `d=a/A/i/I/n/N/c/C/p/P` (решта значень ігнорується); відповіді `OK`/`ENOENT`/`EINVAL`/`EFBIG`/`ENOMEM` пишуться в PTY;
  - **Unicode placeholders** (`U=1`, U+10EEEE + діакритики рядка/стовпця) — повністю: колір переднього плану = id, колір підкреслення = id розміщення, третій діакритик = старший байт id; пропущені діакритики успадковуються від лівої клітинки;
  - **iTerm2** `OSC 1337 ; File=…inline=1` (`width`/`height`: N клітинок, `Npx`, `N%`, `auto`; `preserveAspectRatio`), PNG/JPEG/GIF (перший кадр)/WebP;
  - **Sixel** — розпізнається і відкидається (нічого не друкується), без декодування; DA1 лишається `?6c`, без `;4`.
- Модель: кожне розміщення — це клітинки-плейсхолдери в сітці alacritty (так само, як у kitty). Тому зображення скролиться, переформатовується й стирається разом із текстом, живе в scrollback і належить своєму екрану (alt-screen не протікає назад). Сховище (`images.rs`) тримає лише дані (RGBA, `Arc`) і геометрію пари (image, placement). Бюджет 32 МБ на термінал, витіснення LRU (спершу зображення без розміщень). Максимум 4096 розміщень. Наближення: `ESC c`/ED 2 стирають клітинки (отже й картинки), але дані лишаються в сховищі до витіснення; `d=a` видаляє всі розміщення, а не лише видимі.
- Курсор після зображення (якщо не `C=1`): на останньому рядку зображення, у стовпці одразу правіше (`layout_sequence` + `cursor_sequence`, тестується); для iTerm2 так само. Зображення ширше за екран обрізається, а не переноситься; автоматичний розмір зменшується до доступної ширини.
- Малювання (`element.rs`): клітинки-плейсхолдери збираються під час обходу сітки, зливаються в смуги по рядках (`build_strips`) і малюються `window.paint_image` поверх фону до тексту; геометрія в пікселях (`strip_geometry`) враховує обрізання, letterbox і частково прокручене зображення. `RenderImage` (BGRA) кешується по `ImageData.uid` (до 48 шт., зайве скидається з атласу). Виділений текст копіюється без плейсхолдерів (`strip_placeholders`).
- Відповіді на запити розміру: `CSI 14 t` відповідає alacritty (`ESC[4;<h>;<w>t`, піксельний розмір клітинки передає `resize`); `CSI 16 t` alacritty не підтримує, тому відповідь `ESC[6;<h>;<w>t` формує наш фільтр.
- Змінна `CLAUDE_CODE_FORCE_TERMINAL_IMAGES=1` примусово додається в середовище терміналів (`crates/daemon/src/env.rs`, як `TERM_PROGRAM`; потребує одного перезапуску демона), щоб Claude Code показував картинки.
- Вставка зображення з буфера (`paste_image.rs`, `view.rs`): якщо в буфері є зображення без тексту, воно кодується в PNG у `<temp>/sich-paste/paste-<мс>-<n>.png` (файли старші за 24 год видаляються при старті), а шлях вставляється як текст (з лапками, якщо є пробіли). Для терміналів із агентом Claude/Codex вставка завжди в bracketed-режимі (`TermSession::paste_bracketed`), для решти — звичайним текстом (bracketed лише якщо його ввімкнула програма).

## Вбудований ConPTY (Windows, `third_party/conpty/`)

Системний ConPTY (kernel32) відкидає APC-послідовності, тож Kitty graphics (`ESC _ G … ESC \`) не доходять до PTY. Тому разом із `sich.exe` постачаються офіційні `conpty.dll` + `OpenConsole.exe` з NuGet-пакета `Microsoft.Windows.Console.ConPTY` 1.25.261109001 (Microsoft, MIT; версія й SHA-256 у `third_party/conpty/README.md`, ліцензія в `THIRD_PARTY_NOTICES.md`).
- Завантаження: `portable-pty` сам намагається відкрити `conpty.dll` за простим іменем (шукається поруч з exe) і лише потім бере kernel32; прапорці не змінювались. `OpenConsole.exe` має лежати поруч із dll.
- Доставка: `crates/app/build.rs` копіює файли в каталог профілю cargo поруч із `sich.exe`; `daemon_host::relocate` копіює їх з каталогу вихідного exe в `daemon-host/<build_id>/` (атомарно, незмінні файли не перезаписуються).
- Фолбек: якщо файлів немає чи копіювання не вдалось - лише попередження в лог, використовується системний ConPTY (APC тоді губляться, решта працює).
- Тест `crates/daemon/tests/conpty_apc.rs` перевіряє, що APC доходить до читача.
